# OpenLEO v1.0 release criteria

v1.0 is the reproducible research release, not a renamed development snapshot.
It must let another researcher inspect the assumptions, reproduce the benchmark,
consume its link traces and verify the conclusions without undocumented local state.
“Complete” applies to that declared scope, not to every satellite, channel or network.

## Current capability: v0.4

| Area | Implemented | Remaining boundary |
| --- | --- | --- |
| Orbital geometry | Archived GP/SGP4 propagation, worldwide station inputs, UTC/ECEF provenance, independent local-geometry checks | Fitted elements are not truth; no orbit covariance or observation-based error estimate |
| RF model | Free-space budgets, fixed receiver noise, five cited DVB-S2 reference modes and explicit implementation margin | No measured terminal, antenna pattern, interference, acquisition or modem simulation |
| Reference atmosphere | P.835-7 profile, P.453-14 refractivity, P.676-13 slant loss, endpoint refraction and excess delay; official and analytic checks | Global reference conditions, not local weather; fixed noise temperature; spherical, non-dispersive ray approximation |
| Network experiment | Fixed-capacity, minimum-delay and maximum-bottleneck snapshot routes | No traffic, contention, queues, protocol goodput or validated packet-simulator adapter |
| Experiment design | Pass-level deterministic sensitivity; free-space/reference propagation ablation and layer refinement | No probabilistic uncertainty result or complete multi-scenario fidelity study |
| Application | Local editing, 3D geometry, synchronized plots/readouts, offline reports and versioned CSV/JSON exports | Visualization is of model outputs, not live telemetry or independent validation |

Commands and current model bounds are in [WORKBENCH.md](WORKBENCH.md). Verification
evidence and what it cannot establish are in [VALIDATION.md](VALIDATION.md).

## Gates before the v1.0 tag

### 1. Freeze the supported scientific scope

- [ ] Publish the final input/output schemas, supported domains, units, time and frame
  conventions, dependency versions, migration policy and unsupported effects.
- [ ] Define the questions and comparison cases before interpreting their results:
  orbital geometry, free-space RF, reference atmosphere, adaptation and fixed-capacity
  baseline must be separable. Test more than one station, frequency and RF margin.
- [ ] Give acquisition, handover, directional-terminal and receiver-noise assumptions
  explicit treatment. Either validate a bounded implementation or show why its omission
  does not support the chosen claims; do not infer failed handovers from route switches.
- [ ] Include statistical rain/cloud or weather-driven models only after separate
  current-version reference checks, data/terms review and declared temporal meaning.
  Reference-profile results cannot support a weather-aware conclusion.

### 2. Complete the evidence package

- [ ] Run controlled ablations with sampling and layer-resolution checks; record effect
  sizes and cases where more model detail does not change the conclusion.
- [ ] Supply a justified uncertainty budget. Separate input assumptions, numerical
  resolution and model discrepancy; use probability distributions and correlations
  only where evidence supports them. Deterministic sweeps are not uncertainty bars.
- [ ] Add at least one independently sourced observational comparison for the quantities
  claimed as observed, with timestamp, station, orbit, processing and calibration
  metadata. Geometry/Doppler evidence alone does not validate Ku/Ka received power.
- [ ] Obtain independent scientific review of equations, reference cases, datum handling,
  loss/noise coupling, delay and all empirical claims. Resolve important findings.

### 3. Validate network consumption

- [ ] Deliver a version-pinned, small packet-simulator adapter, keeping it outside the
  core physics. Test trace units, timestamps, rate changes and outages end to end.
- [ ] Match analytic constant-link and outage cases before comparing fixed and dynamic
  traces. Record traffic assumptions, seeds, routing/sampling intervals and overheads.
- [ ] Report packet loss, RTT or goodput only from an appropriate packet experiment;
  retain “reference rate” and “snapshot bottleneck” labels elsewhere.

### 4. Verify and archive the release

- [ ] Regenerate the frozen benchmark and every publication figure/table using one
  documented command in a fresh environment, with input and output fingerprints.
- [ ] Pass unit, integration and browser checks, at least 80% coverage, wheel/sdist
  inspection and the Linux/macOS/Windows matrix for the release commit.
- [ ] Demonstrate that both live editing and exported offline reports preserve the
  scientific data, units, model limitations and provenance. Test invalid inputs and
  the local application's HTTP/security boundaries.
- [ ] Finish the methods, results, limitations, source attribution and novelty review;
  make the public artifact independently usable without access to a draft manuscript.
- [ ] Resolve critical/high review findings, freeze release notes and citation metadata,
  and archive the exact software and distributable derived data with persistent DOI(s).

These gates are not yet complete. A paper submission or acceptance is not guaranteed
by a software release. New capabilities require their own evidence; hardware control,
real commercial-network reconstruction, a new orbit propagator and waveform decoding
are not v1.0 requirements.
